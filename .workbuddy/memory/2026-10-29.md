## 稳定失败清单攻坚（问题① 收尾，同日第二段）

### 核心诉求
失败清单要稳定在 7-8 条（同一变量下多次跑，失败题集合稳定），之前 7→3→4 条波动不合格。

### 根因定位
- 评测 `results_equal` 默认 `ordered=False`（多重集比较），但失败清单里的差异实际是"模型漏写次级排序键 → SQLite 对并列行按 rowid 返回 → LIMIT 截断选中不同并列行 → 多重集不同"。
- **不稳定根因**：题目明确写了"XX 相同时按 YY 升序"时，模型会照抄次级键 → 题就通过了。只有"题面只写主排序键、不提示次级键"时模型才漏写。
- ec-003 之所以稳定失败，正因为它的题面只写"按订单数降序"，没写次级键。

### 关键机制：深并列（并列深度 >> 剩余名额）
稳定失败 = 题面只写主排序键 + 并列深度远大于 LIMIT 剩余名额。gold 用 `ORDER BY x DESC, id`，模型漏 id 时 SQLite 按 rowid 返回，几乎必然与 gold 的 `id ASC` 不同。

- 加强 ec-004（Top10→Top13）、ec-005（Top13→Top40）、ec-013（修正 gold_tables order_items→orders + 移除次级键提示）。

## chinook 稳定失败清单（问题① 第三段，同日）

### 关键差异：chinook 数据按主键有序，漏键机制需变体
- chinook 所有表 rowid == 主键（按主键顺序插入），SQLite 对 GROUP BY 的并列行恰好按主键序返回，导致"漏写主键次级键"**不失败**（与 ecommerce 数据乱序不同）。
- **破解**：gold 的次级排序键用**非主键字段**（姓名/标题/国家名），题面仍只写主排序键。模型漏次级键时 SQLite 按主键（rowid）返回并列行，与 gold 的姓名序不同 → 稳定失败。

|---|---|---|---|
| ch-002 | 国家销售额 Top20 | 7抢3 | BillingCountry |
| ch-005 | 客户消费额 Top30 | 30抢2 | LastName+FirstName |
| ch-011 | 专辑曲目数 Top80 | 34抢1 | Title |
| ch-013 | 艺术家售出升序 Top32 | 31抢1 | Artist.Name |

### 改动明细
- ch-002（国家消费额 Top5→Top20）、ch-005（客户消费额 Top5→Top30）改造。
- ch-011（原员工列表，太简单）→ 专辑曲目数 Top80；ch-013（原时长 Top10 简单题）→ 艺术家售出曲目数升序 Top32。
- 全部"题面只写主排序键"，gold 用非主键字段做次级键。
- 30 题 gold 全部验证通过（编号 ch-001~ch-030 连续）。
- 题型分布：simple=5, aggregation=6, join=8, nested=5, ambiguous=4, adversarial=2。

### 教训（chinook 专属）
- 数据"按主键有序"的库，深并列漏键机制必须换成"gold 次级键用非主键字段"，否则 SQLite 恰好按主键返回并列行、题目失效。
- 用户目标失败 4-5 条，加上 ch-010 原有的列数陷阱（模型偶尔失败），失败清单约 4-5 条。

## sakila 稳定失败清单（问题① 第四段，同日）

### 关键发现：sakila 几乎全库有序，只有 rental 表 rowid 乱序
- sakila 大部分表（actor/film/customer/payment/inventory/category/city）rowid == 主键，且 film.title、city.city 等文本字段恰好字母序 == 主键序 → 电影/城市维度的"漏次级键"机制天然失效。
