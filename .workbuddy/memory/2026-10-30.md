## Day 6 §1.6 验收 bug 修复

- **现象**：`ask` 命令的 answer_text 输出"各国客户总消费额前5名共48行，当前展示前10行。"——结论空洞（只说元信息，未点名实体/数值）。
- **根因**：`node_compose` 的 `COMPOSE_USER` 漏传列名，`sample` 用裸元组 `str(tuple(r))` 拼装，模型面对无表头数据只能瞎猜，吐"消费额介于37.62至42.62"这类无意义结论。**不是没走 LLM**（llm_calls=4，多 1 次即 compose），而是走了 LLM 但输入缺列名。
- **修法**：`terminal_nodes.py` 改两处——① `COMPOSE_USER` 加 `{columns}` 占位符 + "点名关键实体和数值"的要求；② `sample` 改为带表头（`header + body`），并传 `columns` 进 format。
- **验证**：修复后结论变为"仅展示前10行：奥地利 Astrid Gruber 42.62、巴西 Luís Gonçalves 39.62 等各国客户总消费额前5名。"——真正回答问题。

## Day 6 §1.6 二次验收：RANK 并列 bug（做 C）

- **现象**：改列名后结论已点名实体，但 SQL 用了 `RANK()`（并列跳号），导致"前 5 名"实际多于 5 人（Brazil 第 2 名 4 人并列 37.62 → 总行数 48→53，Canada 8 人/USA 7 人溢出）；结论出现病句"巴西第2名均为37.62"。
- **根因**：题目"前 N 名"未写死并列口径，模型在 ROW_NUMBER/RANK 间摇摆——与 Day 5 ec-011/016/017 的 tie-breaker 是同一类病。
- **修法（方案 C）**：① `a0.py` 的 SYSTEM 加"排名口径"硬规则（前 N 名默认 ROW_NUMBER() 恰 N 行，禁 RANK/DENSE_RANK，排名窗口带稳定 tie-breaker）；② Day 6 手册 §1.6 补三条验收标准（点名实体+数值 / 不含并列歧义 / SQL 窗口函数正确）。
- **验证**：改后实测 SQL 用回 ROW_NUMBER()、结论正确点名"奥地利 Gruber 42.62、巴西 Gonçalves 39.62、加拿大 Tremblay 39.62"，无病句。

## Day 6 §3 可观测（tracer）接入

- **背景**：tracer.py / trace_viewer.py 之前已写好但未接入，client.py 里 grep 不到 tracer，跑任何东西都不产 trace。
- **接入改动**：① `client.py` 的 `LLMClient.__init__` 加 `tracer` 参数，`chat_json` 成功/缓存命中各记一条 `llm_call` 事件（含 model/in_out_tokens/cost/latency/cache_hit）；② `graph.py` 的 `_get_client` 和 `build_graph` 加 `tracer` 参数并透传到 6 个 LLM 节点；③ `cli.py` 的 `ask` 命令加 `--trace` 可选参数，开启时创建 Tracer、先 log `question` 事件、跑完 close；④ `tracer.py` 加 `threading.Lock`（runner 4 线程并发写安全）；⑤ `trace_viewer.py` 改进：llm_call 事件归到最近一次 question 事件下，显示模型名+cache 标记。
- **踩坑**：`llm_calls=15` 但 trace 仅 3 条的矛盾，根因是 `checkpoints-cli.db` 残留历史 checkpoint（反复用同一 thread_id `cli-default`），langgraph 恢复旧执行历史累加了 llm_calls。换全新 thread_id 后 llm_calls=3 与 trace 3 条严格一致。**教训：ask 演示/评测都要用唯一 thread_id，否则 checkpoint 污染**。
- **用法**：`python -m src.datapilot.cli ask "..." --trace experiments/trace/demo.jsonl` 产 trace，再 `python -m src.datapilot.obs.trace_viewer experiments/trace/demo.jsonl` 看调用树。
