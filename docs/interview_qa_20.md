# 面试自问 20 题（参考答案）

> 用途：面试前默讲。每题控制在 3 分钟内讲完，重点是「数字 + 决策逻辑 + 诚实的负结果」，不要堆技术名词。
> 所有数字可溯源到 `reports/ablation.md`（v2）和 `docs/design.md`。

---

## 1. 为什么用「评测先行」而不是先写 Agent 逻辑？

先写 Agent 会陷入「我加了个东西，感觉变好了」的自我感动，没法回答「这东西到底有没有用、代价多大」。评测先行是先把「什么叫对」定义清楚——我用**执行结果等价（EX）**而不是文本相似度做判定，然后从最朴素的 A0 基线（裸 LLM 直接生成 SQL）开始跑，后续每一个组件（检索/修复环/gate/verifier/缓存）都是**在 A0 之上做消融**，用 EX 的变化量化它的净收益。

好处有两层：一是每个组件都能量化「值不值」；二是造评测集这件事本身就逼我把业务口径（GMV 算什么、成交算哪些状态）先想清楚，否则 gold 答案都没法写。结果就是：别人说「我们提升了准确率」，我能说「检索让 sakila 掉了 16.6pt，但修复环又赚回 5.6pt」——这是评测先行才拿得到的话。

---

## 2. A0 基线为什么重要？headroom 是什么？你的三库 A0 分别是多少？

A0 是「裸模型直接生成 SQL」的下限能力，它是所有消融的参照系。没有它，A3 的 83.3% 无从谈起——你都不知道是组件带来的还是模型本来就这么强。

**headroom** 是「A0 到 100% 之间的距离」，也就是可供组件提升的空间。A0 越高，headroom 越小，组件能证明的价值就越少。

我的三库 A0：**chinook 75.0%、sakila 72.2%、ecommerce 88.4%**。ecommerce 的 88.4% 已经越过 85% 红线，headroom 不足——所以我在报告里诚实标注了这点，不硬吹 ecommerce 的「组件收益」，而是强调 chinook/sakila 才是 headroom 充足、能讲消融故事的库。

---

## 3. 为什么第三个库要自建？防污染怎么论证？

chinook/sakila 是公开教学库，模型训练语料里大概率见过它们的 schema 甚至原题，所以这两库上的高准确率有「背过」的成分，无法证伪。

自建 ecommerce 用 **seed=42 确定性生成 12 张表**，schema、表名、列名、数据都是模型绝对没见过的。它上面的 EX 才是**泛化能力的下限估计**——88.4% 说明「即便模型从没见过这套 schema，裸能力也能到 88%」。这是防污染的核心论据：把一个模型「没见过」的库当作更可信的评估面。同时 seed 固定保证可复现，别人能复刻出同一套数据。

---

## 4. BM25 检索比全量 schema 好在哪？代价是什么？

好在**控输入 token**：大库全量 schema 又贵又可能让模型在无关表上分心。BM25 + 外键一跳检索，只把相关的表/列喂给模型，省 token、降干扰。

代价是**漏召会直接砍 EX**。我的实测很清楚：A1 三库**全比 A0 低**——sakila 从 72.2% 掉到 55.6%（-16.6pt）、ecommerce 从 88.4% 掉到 81.4%。漏召一个关键表，SQL 直接没法写对。这就是「省 token 的代价」，也是 A2/A3 修复环存在的前提——修复环通过 escalate（退回全量 schema 重生成）把漏召补回来。

---

## 5. 修复环里 escalate 和 repair 的区别？为什么 escalate 更关键？

- **repair**：语法错/执行错时，带着 sql_history 让模型修 SQL 语法。
- **escalate**：诊断出「schema 疑似不全」（漏召）时，一次性**退回全量 schema 重新生成**。

为什么 escalate 更关键：Day 3 我实测发现，失败几乎全是**检索错（schema 不全）而非语法错**。模型很少写错语法，但常常因为没拿到正确的表/列而写出逻辑错的 SQL。所以修复环的核心是 escalate 而不是逐条修语法。这是「修复环的形态要由失败分布驱动」的教训——不能想当然地以为失败是语法问题。

---

## 6. 为什么修复上限设 3 轮？

防死循环的硬上限。修复环是「执行反馈驱动」的，如果不设上限，一个修不好的题会无限重试，烧 token 又烧时间。3 轮是我观察到的「收益拐点」——大部分能修好的题 1~2 轮就修好了，超过 3 轮基本是语义上无解，直接 give_up 更诚实。**这也是「可靠性优先于覆盖率」的一部分**：与其死磕一个大概率错的答案，不如明确说「修不好」。

---

## 7. gate 的三分类怎么判定？fail-open 是什么意思？

gate 在最前面把问题分成三类：
- **answer**：能答，放行到 retrieve。
- **clarify**：有歧义（比如「客户」指哪张表），用 `interrupt()` 反问澄清，等人回答。
- **refuse**：危险（写操作）或超纲，直接拒答。

**fail-open** 指「拿不准时偏向放行（answer）而不是误拒（refuse）」。Day 5 我用「fail-open 收紧」——题面已经给了口径（比如明确写了 `status='on'`）就判 answer，把三库误杀（gate_false_kill）从 6/8 **归零**。核心取舍：一次误拒丢的是覆盖率，一次误放（硬答）产生的是「看起来对其实错」的答案，后者危害大得多。

---

## 8. verifier 为什么降级？这是你最该讲清的一个负结果。

原设计：verify 用 LLM 做「SQL ↔ 问题 ↔ 结果」的对齐判断，判错打回 repair。实测三库 **verify_fixed 全 0**——LLM judge 一题都没救回来，却买到了 0 误杀、代价是 token +150%。

所以按决策树把它砍了：**降级成确定性 guard**，只留 `deterministic_flags`（整列 NULL / 全 NULL / 截断）做零成本兜底。降级后重跑，EX 不降反升（chinook_a3 79.2%→83.3%、ecommerce_a3 81.4%→90.7%）。

这个负结果的价值在于：**我做了个没用的东西，用数据证明它没用，然后把它砍了**——这是完整的工程闭环，比「verifier 提升了 2 个点」可信得多。面试必讲，因为它证明我会归因、敢砍，而不是堆功能。

---

## 9. EX 用什么比较？为什么不用文本相似度？

EX 用**执行结果等价**比较：把 gold_result 和预测 SQL 的实际执行结果都做 `normalize_rows`（多重集归一化），再按是否 `order_sensitive` 比较，多重集相等才算对。

不用文本相似度的原因：SQL 写法千千万，`WHERE status='on'` 和 `WHERE status IN ('on')` 文本不同但结果一样；反过来两个写法完全不同的 SQL 可能结果一样。文本相似会同时产生误判和漏判。**执行结果才是「对不对」的唯一真相**——你要的是数据对，不是 SQL 长得像。

## 10. 三段式指纹是什么？解决了什么问题？

三段式指纹 = **数据集 + prompt + 配置**三者的哈希。它解决的是「**静默续跑混数据**」——我改了一处 prompt，但 runner 没察觉，把新题续跑进旧的 run_id，导致结果里混了新旧两版 prompt 的数据，数字就脏了。

做法是把指纹写进 run_id 或校验里：只要三者任一变了，指纹就变，旧 run 不能续跑、必须重跑。这是「每个数字可溯源」的工程保障——面试官问我某个数字哪来的，我能精确指到 `experiments/runs/v2_{库}_{配置}` 和一个具体指纹（v2 是 `c1038e268edf`）。

## 11. 错误自信率是什么？你的数字是多少？为什么重要？

错误自信率 = 抽评的结论里「做了**结果集不支持的断言**」的比例——即模型**答错还自信**（编造数值、把样本当全体、把相关当因果、忽略 NULL/截断）。

我人工抽评了 30 条结论，**2/30 ≈ 6.7%**。两条分别是「截断当全体」（只展示前 10 行却暗示全月规律）和「NULL 未标注」（把 city 为 NULL 的订单当成一个叫 None 的城市）。

为什么重要：EX 只衡量「结果对不对」，衡量不了「模型有没有对错误结果编一句笃定的话」。**错误自信率抓的是 EX 抓不到的那一层——可信度**。而且我这个 6.7% 是「主动设计出来的好结果」：composer 加了「严格基于结果集」的约束，所以两条都不是编造幻觉，只是表达边界瑕疵。这比「我们准确率高」锋利得多。

---

## 12. 缓存 + 路由（A4）的价值在哪？temperature=0 下缓存为什么对单次评测无效？

A4 = 缓存 + 路由。**路由**指「简单题走小模型/短链，难题走大模型」，省成本。**缓存**指 LLM 响应缓存，同输入直接命中。

但 **temperature=0 下缓存对单次全量评测几乎无效**——因为评测里每道题都是唯一的、只问一次，缓存没有「第二次命中」的机会。缓存的真正价值在**开发循环和 demo**：我反复调 prompt、反复跑同一批题时，命中的那部分不再花钱、不再等延迟。所以 A4 的消融里，EX 没有提升（chinook_a4 甚至降到 79.2%），它的收益是**成本/延迟维度**而非准确率维度——这也是一个诚实的结论：A4 不是「更准」，是「更省/更快」。

## 13. 小样本波动怎么处理？1 题 = 几个点？

我的评测集是 30/20/60 题，样本很小。**1 题 = ±4pt**（1/25 ≈ 4%，1/60 ≈ 1.7%，取 chinook/sakila 的尺度约 ±4pt）。所以我给自己定了一条纪律：**±5pt 内的差异不下结论**——比如 sakila 的 a3（72.2%）和 a0（72.2%）持平、chinook_a2（70.8%）比 a1（75.0%）低，这些我都如实记录但不解读成「组件有害/有益」，因为都在噪声带内。这是「小样本下的诚实」：宁可说「不构成结论」，也不硬从噪声里读出趋势。

## 14. 你的评测有哪些局限？

三条，主动承认：
1. **headroom 不足**：ecommerce 的 A0=88.4% 越过 85% 红线，难题对当前模型不够难，评测难度还需上调。
2. **小样本**：30/20/60 题，1 题 = ±4pt，所有「增益」都要在噪声下解读。
3. **错误自信率样本少**：只抽评了 30 条，6.7% 是点估计，样本不够大。

另外还有两个已知的系统性短板：**枚举值猜错**（`status='on'` 被猜成中文）和**排序并列（tie-breaker）**。这些我都写在 design.md 的「局限」里，不藏。

---

## 15. 排序题并列（tie-breaker）为什么是难点？你怎么处理的？

「前 N 名」这类题，模型在 `RANK()` / `ROW_NUMBER()` / `DENSE_RANK()` 之间摇摆，没吃准「并列」的语义：是要**恰好 N 行**（ROW_NUMBER），还是**前 N 个名次**（RANK 会跳号、DENSE_RANK 会挤名次）。并列时 RANK 会导致「前 5 名」实际多于 5 人。

我的处理是**写进 SYSTEM 的硬规则**：「前 N 名默认用 `ROW_NUMBER()` 取恰好 N 行，禁用 RANK/DENSE_RANK，排名窗口必须带稳定 tie-breaker」。这是根治（覆盖 A0~A4 所有 generate）而非逐题补丁。这个坑也让我意识到：**语义约束要显式化进 prompt**，不能寄望模型自己判断。

---

## 16. 枚举值（status='on'）猜错是什么问题？根治办法？

问题：schema 里只给了列名 `status`，没给它的取值，模型会**猜**——比如把「在售」猜成 `status='在售'` 或 `status='on_sale'`，而库里实际是 `status='on'`。这是反复出现的系统性短板（Day 2 就发现、Day 5 复发）。

根治办法是**枚举值采样进 schema**：建 schema 时就对低基数列（status、active、method）采样 distinct 值，把「status 取值 ∈ {on, off}」喂给模型，而不是让它猜。我当前用的是「口径进 prompt」的折中（把成交口径、在售口径写进 SYSTEM），但根治是 schema 枚举采样——这是我在 design.md 里明确的「待补」。

## 17. checkpoint 污染是什么坑？怎么避免？

LangGraph 的 checkpointer 用 SQLite 持久化图状态，key 是 `thread_id`。如果 ask/eval 每次用**同一个 thread_id**，上一次的中间状态会残留，污染下一次执行（比如上一条题的状态被当成当前题的输入）。

避免方法：**每次执行用唯一 thread_id**，我的约定是 `thread_id = 配置:题id`，保证不同 run、不同题之间状态彻底隔离。这跟三段式指纹是同一类问题——都是「静默的状态污染」，都要靠**显式的唯一标识**来杜绝。

## 18. composer 为什么用 LLM 生成结论而不是规则拼装？

因为交付物是「可信的自然语言结论」，不是「一张裸表」或「规则拼出来的模板句」。用户（不会写 SQL 的业务/产品）要的是「奥地利 Astrid Gruber 42.62 是最高消费」，这句需要理解结果集里谁是实体、哪个是数值、怎么排序——这是语义任务，规则拼装只能出「共 48 行，展示前 10 行」这种空洞模板。

代价是 composer 这一步会多一次 LLM 调用（+token），而且它自身也会犯错（所以才有错误自信率这个指标来约束它）。我用「严格基于结果集」的约束 + 传列名（`{columns}`）来压它的过度断言。**权衡**：规则拼装零幻觉但没价值，LLM 生成有价值但要约束——我选后者，因为「结论」正是这个产品区别于「SQL 翻译器」的地方。

## 19. 单题成本怎么算的？你的 A4 单题多少钱？

单题成本 = 该配置下所有题的平均 LLM 调用成本，按 token 计价（输入/输出分开算，再按模型单价折成人民币），我直接聚合到 `cost_per_q_cny`。

我的 A4 单题成本（v2）：**chinook ¥0.0145、sakila ¥0.0125、ecommerce ¥0.0080**。可以看到 A4 因为缓存+路由，ecommerce 从 a3 的 ¥0.0097 降到 ¥0.0080，sakila 从 ¥0.0150 降到 ¥0.0125——这是 A4 在成本维度的真实收益（而不是准确率维度的）。

## 20. 如果重来一次，你会先做什么、不做什么？

**先做**：
1. **评测集先于一切代码**，而且第一天就把「枚举值采样」和「tie-breaker 口径」写进 schema 和 SYSTEM——这两个坑我反复踩了两次。
2. **先把失败分布摸清楚再设计修复环**——我 Day 3 才意识到失败是「检索错」而非「语法错」，如果一开始就盯着失败分布设计，escalate 会更早做对。

**不做**：
1. **不先写 LLM verifier**——我花了一整轮证明它零收益再砍掉。如果一开始就意识到「执行结果已经是客观判据，LLM judge 是冗余的」，这步能省下 +150% 的 token。
2. **不在小样本上过度解读**——sakila 那些 55.6% vs 66.7% 的波动，我一度想读出趋势，后来学会「±5pt 内不下结论」。早明白这点能少走弯路。

一句话总结教训：**评测先行 + 失败分布驱动 + 诚实归因（包括砍掉没用的东西）**，比堆组件重要得多。
